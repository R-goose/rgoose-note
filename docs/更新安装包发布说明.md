# 更新安装包发布说明

本文说明如何为 R-Goose Note 制作、发布和验证新版安装包。当前发布流程已经配置为在
本机 macOS Runner 上自动构建，并上传到公开的 Gitee `latest` Release。

## 一句话流程

更新 `package.json` 中的版本号，提交并推送代码，然后推送同名版本标签（例如
`v2.5.1`）。GitHub Actions 会在这台 Mac 上构建安装包并发布到 Gitee。

```text
提交版本代码 → 推送 v2.5.1 标签 → 本机 Runner 构建 macOS + Windows
                                              ↓
                                      上传 Gitee latest Release
                                              ↓
                             用户下载安装包 / 已安装应用检查更新
```

> 只有推送 `v*` 格式的版本标签才会发布；普通代码提交不会自动替换线上安装包。

## 发布新版本

假设本次版本要从 `2.5.0` 升级为 `2.5.1`：

1. 将 [`package.json`](../package.json) 中的 `version` 改为 `2.5.1`。
2. 完成代码修改和必要测试，提交并推送 `master`。
3. 在已推送的提交上创建并推送版本标签：

   ```bash
   git tag v2.5.1
   git push github v2.5.1
   git push origin v2.5.1
   ```

4. 打开 GitHub 仓库的 **Actions → Build and publish release**，确认任务由
   `rgoose-note-mac` 接走并最终显示成功。
5. 打开 [Gitee latest Release](https://gitee.com/kokomi123/rgoose-note/releases/tag/latest)，
   核查附件和版本号。

工作流会校验标签和 `package.json` 一致。例如 `v2.5.1` 必须对应
`"version": "2.5.1"`；不一致时会在打包前失败，避免发布错版本。

## 当前产物

| 平台与用途 | 用户应使用的文件 | 保留原因 |
| --- | --- | --- |
| macOS Apple Silicon 手动安装 | `R-Goose Note-<版本>-arm64.dmg` | 用户双击后拖入“应用程序”即可安装。 |
| macOS 应用内自动更新 | `R-Goose Note-<版本>-arm64-mac.zip`、对应 `.blockmap`、`latest-mac.yml` | `electron-updater` 需要 ZIP 更新包；即使主要提供 DMG 下载，也不能删除。 |
| Windows x64 手动安装 | `R-Goose Note Setup <版本>.exe` | 适用于主流 Intel/AMD Windows 设备。 |
| Windows 应用内自动更新 | `.exe.blockmap`、`latest.yml` | 供差分更新和版本识别使用。 |

发布脚本会先删除 `latest` Release 中已有的 macOS/Windows 更新附件，再上传当前版本的一整套文件。因此 Release 中不应长期保留重复的 `latest.yml` 或旧版本安装包。

## 用户如何安装和更新

### macOS

用户下载 `.dmg`，双击打开后将 **R-Goose Note** 拖到“应用程序”文件夹。当前构建未进行 Apple Developer ID 签名和公证，浏览器下载的 DMG 会被 macOS 标记为网络来源，Gatekeeper 可能显示“已损坏，无法打开”。这通常不是文件真的损坏，而是签名/公证校验未通过；仅限自己确认来源可信的测试，可执行：

```bash
xattr -dr com.apple.quarantine "/Applications/R-Goose Note.app"
```

正式向其他 Mac 用户分发时，应配置 Apple Developer ID 签名与公证，而不是让用户绕过 Gatekeeper。

应用内更新仍依赖 Release 中的 ZIP 和 `latest-mac.yml`，无需用户手动下载 ZIP。

### Windows

用户下载 `R-Goose Note Setup <版本>.exe` 并运行安装。安装完成后的应用会通过
`latest.yml` 检查后续版本更新。

## 已配置的自动发布环境

- GitHub 仓库 Secret：`GITEE_TOKEN`，仅工作流读取，绝不能写入代码、日志、截图或文档。
- Runner：`rgoose-note-mac`，运行于本机 macOS，标签为
  `self-hosted`、`macOS`、`ARM64`、`rgoose-note-release`。
- Runner 服务：以 macOS LaunchAgent 自动启动；如果 Actions 长时间停在“等待 Runner”，先检查 Runner 是否在线。
- 构建架构：macOS ARM64 与 Windows x64。Windows 安装器由 Electron Builder 的兼容层在 Mac 上生成。

## 发布后检查清单

- GitHub Actions 显示 **success**。
- Gitee `latest` Release 中各附件只保留一份。
- `latest-mac.yml` 指向当前版本的 macOS ZIP。
- `latest.yml` 指向当前版本的 Windows `.exe`。
- macOS 实机可从 DMG 安装并启动。
- Windows x64 实机可安装、启动，并确认笔记数据库可正常打开。

## 常见问题

### Actions 一直处于 queued

这通常表示本机 Runner 未在线。检查 Runner 服务目录：

```bash
cd /Users/szwego/actions-runner-rgoose-note
./svc.sh status
```

如果显示未启动，可执行：

```bash
./svc.sh start
```

### 发布任务失败在 Gitee 上传

先查看 GitHub Actions 中 **Build and publish to Gitee Release** 步骤的具体错误。确认
`GITEE_TOKEN` Secret 仍存在且具备该仓库 Release 的写入权限；不要把令牌复制到聊天、终端历史或仓库文件中。

### 为什么 macOS 同时有 DMG 和 ZIP

DMG 是给用户手动安装的格式；ZIP 是 Electron 自动更新的更新格式。二者用途不同，发布时必须同时保留。

### 为什么 Windows 包是 x64 而不是 ARM64

绝大多数 Windows 电脑使用 Intel/AMD x64。构建机是 Apple Silicon，若不明确指定架构会错误地产出 Windows ARM64 包；发布脚本已固定为 Windows x64。
